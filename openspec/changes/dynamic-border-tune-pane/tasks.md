## Defects found only by running the app (this session)

The previous session's blocker was "los cambios no se aplican — el grosor del borde y todo el apartado". Reproducing it in the running app surfaced defects that no render test could ever see. All are fixed; each has a regression test or a file-level before/after in the handoff.

1. **`notify-tune-changed` passed its arguments shifted by one** (`BordersSection.slint`). The call inserted `tune-color-count` as the 2nd argument and dropped `tune-animations`, so Rust received the slot count as the *angle*, the angle as the *inactive colour*, the inactive colour as the *glow* and the glow as the *animations*. It compiled because Slint coerces the int angle into the string parameter. Fixed to `(colors, angle, inactive, glow, animations, rule)`.
2. **The size slider zeroed the geometry.** The debounce sent `apply-geometry(size, 0, 0, 0)` and the Rust handler writes all four values, so every thickness change destroyed `border_radius` and `gaps_in/out` on the desktop (reproduced: `border_size=4, gaps_in=0, gaps_out=0`, and the `decoration { rounding = 32 }` block removed from the overlay). The U3 rebuild had already removed the radius/gap controls, so the user could not restore them from the UI. Now sends the real `geom-radius` / `geom-gap-in` / `geom-gap-out`.
3. **A `size-init` flag swallowed the first edit of every session** (arrow or drag), which is what made a single thickness change appear to do nothing. Removed; the debounce timer now applies unconditionally, because `geom-dirty` is only ever raised by a user edit.
4. **The gradient angle had no route to Rust at all.** Neither the 30/45/90 buttons nor the arrow cycle notified, so an angle could never be applied. New `angle-changed` callback + notify.
5. **The floating-rule toggle's mouse path never notified** — only the keyboard path did.
6. **Committing any custom colour from the picker panicked the whole process**: `decode_colors` assumed `c:rrggbbaa` while the picker emits `c:#rrggbbaa`, and `hex[i..i+2]` ran past the end of the 9-byte payload (`byte index 10 is out of bounds of '#371e1bff'`). The render test's fixture fed the bare form, which is why it stayed hidden. Now accepts both and can never overrun; regression test added.
7. **Edits were silently refused with no active border preset** (an intentional no-op, so an unsaved draft can never become the desktop's border) and the pane looked merely broken. The refusal is now surfaced in the pane: `TUNE_NEEDS_ACTIVE_BORDER`.
8. The resolved-colour model (`tune-colors-resolved`, which feeds the chips and the picker's seed) was rebuilt only on load/add/remove, so a committed custom colour left the chip — and the next picker seed — stale. Now refreshed on every successful apply.
9. **One mouse-wheel turn permanently killed the pane's keyboard follow.** Both pane `ScrollView`s drove `viewport-y` from a BINDING. Slint drops a property's binding as soon as code assigns it, and the ScrollView assigns `viewport-y` itself on every wheel event — so the first wheel scroll silently removed the binding and the pane never followed the keyboard again for the rest of the session. Navigating to the lower presets then moved the focus to a card that was never scrolled into view: "hay alguno que no se alcanza a ver". Fixed by making the viewport IMPERATIVE (`follow-focus()` called from `changed focused-index` / `changed local-focus` / `changed follow` / `changed editing-slot`) instead of a binding. Found and pinned by a new test, `borders_list_pane_scrolls_with_the_mouse_wheel`, which injects a real `PointerScrolled` event through `Window::dispatch_event` and asserts both halves: the wheel scrolls the pane (2 frames = 25844 ink of 28005 settled, i.e. responsive), and a wheel must not break the follow (measured 30550 of ink when the binding was killed, under 15000 after the fix — read `borders_wheel_follow_{reference,after}.png` to confirm both end on the same focused preset).
10. The Bezier and Style rows had no `TouchArea` at all (see 3.7 above).

## R1 revised: the panel is presented as a floating window (self-preview)

The panel flow used to hold fullscreen from entry to exit — "Holds fullscreen, no window resize anywhere in the flow". That kept the desktop hidden, so a border change could be applied correctly and still never be seen. R1 is revised: while the panel is open, HVE leaves fullscreen, floats and centers itself, so the border Hyprland draws around **HVE** is the live preview of the border being tuned. The window is the preview surface — no second window, and no need to keep any part of the desktop on screen (a side-anchored panel would waste the screen on wallpaper when HVE is the only window open).

- The floating size is derived from the monitor, measured off the surface while it still covers that monitor: no compositor query, no new I/O surface. `SizePolicy::settings_float_size` caps it so a margin survives on every side, because a border flush against the monitor edge is unreadable. On a 1440x900 monitor it resolves to 1000x640.
- `Shell::apply_window_presentation` resolves the presentation from the navigation state. It runs on entry (size + compositor actions) and again when the morph settles (compositor state only, as a re-assert).
- Two findings shaped this, both verified live rather than assumed. A client-side size request is **not** honoured for a floating window in this compositor — the window landed on its minimum — so the resize goes out as an explicit dispatch. And the compositor's restored floating geometry can land after an animation, so the size is resolved exactly once per entry.
- Verified in the running app: the panel floats centered at 1000x640 with the border visible on all four sides, and Escape restores fullscreen 1440x900.

Follow-ups this revision does not cover: the panel is still the inner floating card, and the keeper wants it full-bleed across HVE (that changes the 852px two-column threshold, since the panel goes from 80% to 100% of the window); and the `-- >>> HVE WINDOW RULES <<<` block in `src/settings.rs` still emits its dead `n` placeholder. Note for whoever wires those rules: HVE's `class` is **empty**, so a rule matching `class:` never fires — match `title:` or set the app id in the app first.
